# 信息中心 · 时间管理

语义由你做，日期与校验由内核做。**不心算日期，不手改 JSON。**

> `AGENTS.md` 只讲身份、红线与技能路由；本技能「先读这几条」是行事准则。
> 两者冲突以 `AGENTS.md` 为准。

## 先读这几条（本技能的总规矩）

0. **「提醒我…」不是任务**（用户 2026-11-08）。用户说「提醒我明天中午取快递」「加一个代办
   取快递 明天中午提醒我」这类 —— 它**没有截止、不需要时长、不需要排期**，只是到点说一句。
   写进 reminders，**不要**写进注册表（list.upsert）：
   {"reminders":{"upsert":[{"date":"2026-11-09","time":"12:00","text":"取快递"}]}}
   · 事故（2026-11-08）：登记成**没有 date 的任务** ⇒ 它在注册表里是"永远活跃的活" ⇒
     规划器按课间/整块/晚上不排去搬它 ⇒「明天中午取快递」被扔到了下午 ✗
   · 提醒**不进 slots**：不为它找时段；用户问起才说，别因为它"没排上"去调别的
   · 没说几点 ⇒ 用默认 09:00，并在回话里说一声"按 9:00 提醒"
   · 到点由**管道**直接发微信（不经模型）：你说"提醒已登记"即可，别自己发、也别等
   · 用户说"买好了" ⇒ 同 date/time/text 再写一次，只改 status:"done"
   · 真要花时间做、有截止的才算任务 —— 两者别混。
1. **先登记，再核对。** 有"什么事 + 什么日期"就**先写进去**；不确定就把疑问放在**同一轮回复**里问。
   不要用提问代替登记，也不要为了想清楚反复读注册表。
2. **日期以用户为准。** 课表只是**已录入的课次**，不覆盖调休 / 补课 / 临时调整 —— 不一致听用户的。
   · **周次**（第几周）**不许**：不存、不算、不接受这类输入；**周几**可以（`weekday` 1-7）
   · "这周 / 下周"由我在登记那一刻落成 `YYYY-MM-DD`，并把日期写进回复让他能纠正
3. **循环任务怎么写是我的决定**：内核只保证**同一次发生不物化两条**，并把待决问题报给我
   （`already_present`）。认领 / 改名 / 另立周期任务由我判断后写入。
4. **改 / 删要名字完全一致**（登记新的不受限）；对不上就问，**不翻源码**。
   **过期即默认完成**：不报逾期、不追问、不主动翻旧账；归档后只看清单，要回溯用 `history` / `show`。
5. **规则要少要短。** "今晚有空 / 今晚做任务"这类**只此一次**的话**不许写进 `rules`**，
   只用于这次重排（判断只需问：这是以后都这样，还是就这一次？拿不准当一次性）。
6. **输出短、纯文本**（微信不认 Markdown）；先结论，不复述工具输出。
   **保持简洁直接**：只答被问的（问「带什么」就只答带什么，别把后面几天全列一遍）；
   **调用工具前后不写旁白**（用户看不到你在查什么，只会让输出变长）；手机一屏读完为准。
   问"现在做什么"要给**可执行细节**（题号 / 页码 / 交法 / 在哪交）⇒ **登记时写 `gist`**（≤60 字）。
7. **计划是派生物：注册表一变就从头重排。**
   · 排之前**先过一遍 `planning_rules`** —— 是约束，不是背景资料
   · **先看空档、再估时长，然后往多排** —— 做不完不影响任何东西；轻活按**分钟**算
   · **不要拿旧计划的时段接着用** —— 旧快照只用来对账，不是排期底稿
   · `date` / `due_time` 只装 **DDL**（有就写，没有就不写）；我排的时段只进计划的 `slots`
   · 任务只在**到达 deadline** 或**用户宣布完成**时消失。排过的时段不是 deadline：
     没做就**往后延**，提前做完就把空出来的时段排别的

## 输出格式（三种）

**排版由 `qyn_brief` 生成，不要自己拼**。★ **默认只给规划**；待办 / 日程**等用户点名再给**
★ **默认只展开 3 天**（计算仍按 7 天；末尾一行「后面还有 N 天」）。用户说「这周 / 整周」⇒ 传 `days: 7`；说「就今天」⇒ `days: 1`。
（「待办 / 手头有什么」⇒ `todo`；「日程 / 课表 / 这周怎么安排」⇒ `schedule`）：

- `plan` —— **规划**：带时间、**不含课**；先「现在做什么」块，再按天分块
- `schedule` —— **日程**：课程 + 规划，同一条时间轴按时序混排（课只出现在这里）
- `todo` —— **待办**：两张表（A 按截止日期分组 / B 按紧迫度，**只标 `[急]`**）

拿到 `text` 后**原样发出**，只在「现在做什么」块里补一行 `- 建议：…`（你自己的下一步主张）。
`brief` 的输出就是最终给用户看的文本（纯文本、`- ` 行首、`————` 分天）—— **别改结构**。

★ **`brief` 会把关**（禁止 vs 警告分得很清）：
  · **禁止**（`constraint` 规则的时段、快照过期、撞课、重叠、**课间**、
    **`past_deadline` 排在自己的硬截止之后 = 等于没排**）⇒ `ok=false`，**无豁免**
  · **警告**（`preference` 规则时段、水课、`crosses_deadline` 跨过截止、截止已过的 `past_deadline`）⇒ 放行但带 `warnings`
  · `past_deadline` 的正确处理：**往前挪到截止之前**；**实在挪不进去就醒目地报告用户**
    （哪件事、卡在哪、给可选方案），不要假装排上了 —— 用户 2026-10-15 报过：
    明早 10:10 上课要讲的示例课程作业，被排到了第二天晚上（课堂早过了）。
  · 用户明确同意破例时 ⇒ 把 `allow: [规则id]` 写进**快照正文**（只对 `preference` 生效；
    随快照过期，重排后自然消失）。**没说过不许写**。
  · **短块不是问题**（十几分钟的活本来就该单列，别并块）；**课间没有豁免**：重排避开，
    实在排不下就在回复里说明为什么。
★ 快照过期、或 slots 撞课 / 重叠 / 碰规则时段 ⇒ 它返回 `ok=false` +
  `problems`（**不给 `text`**）。这时**先重排**（改 slots、`qyn_plan_snapshot` 存新的）
  **再调一次 brief** —— 顺序是「重排 → 存快照 → brief」，不要跳过前两步。
★ `plan_snapshot` 会**去重**：slots 与上一份完全一样 ⇒ 不存（返回 `snapshot_unchanged`）。
★ 想改形状 ⇒ 改内核的 `cmd_brief`（那是确定性的排版），**不要在回复里临时发明排版**。
★ 回复里**不要复述工具输出**：`brief` 的正文就是回复主体，前面顶多一句结论。

## 工具用法

**一律用 `qyn_*` 工具**（它们自己知道内核在哪）。
★ 不要用 `pwsh` 去跑内核、也不要去 `read`/`glob` 找 `AGENT/` 下的文件 ——
你的工作目录**不是**仓库根，相对路径会找错地方。要看数据就用工具。

★ **`qyn_apply` 的返回值要看 `check_this`**：`missing` / `replaced` **不是报错**，写入已完成 ——
但它们几乎总是说明**你写错了名字或身份**（要删的没匹配上 / 覆盖了另一门课），
当场改正并告诉用户。

## 写入口 `qyn_apply`

改哪个文件由**内容**决定：课表 → `schedule`，作业/提醒/单次任务 → `list`，规则 → `rules`。
`qyn_mark` 只用于改状态（完成/取消），其余写操作全走 `qyn_apply`。

### apply 怎么写 ⇒ 用技能 `qyn-write`

各种写法的**形状示例**（登记作业 / 改课次地点 / 整周课表 / 调休 / 周期任务 / 规则 / 删条目）
在技能 **`qyn-write`** 里 —— **不确定形状时加载它**，别照记忆猜。

本技能只留两条最容易错的：
- **数组 = 整段替换**；**`{upsert, remove}` = 按身份增量**（只改一两处就用增量）
- 写错键名会**明确报错**，照着报错改即可

### 循环任务怎么写，是**你的**决定（内核不替你判断）

登记**一条**周期任务（`schedule.periodic_tasks.upsert`），再 `qyn_sync` 物化出"这一次"。
**两种模式，看规律跟着什么走**：

| 规律 | 写法 | 例 |
|---|---|---|
| **跟着某门课的课次** | `follow_course`（日期来自录进课表的那节课） | "上课前交""当天布置的作业" |
| **与上课无关的日历规律** | `every` + `weekday`（ISO：1=周一…7=周日）+ `due_time` | "每周三晚上 23:59 交""每天早上" |

★ **别拿 `follow_course` 去凑日历规律** —— 同一门课一周上两次时，它锚到哪一次是不确定的
（会落到**错的星期**）。只要用户的规律**与上课无关**（"每周三交""每天早上"），
就用 `every`/`weekday`。

★★ **有"开始"就说清楚，别让它变成 DDL。**（2026-10-27 加的内核字段）

用户说「周三开始、周五结束」时，**两个日期都要进数据**：
`start` = 周三（最早可开始），`date` = 周五（截止）。
只写一个的日子已经翻过车：Agent 把截止日当成开始，用户第二天问"为什么今天就安排了"。
内核现在会在只读视图里直接给 `starts_in`（"3 天后才能开始"）和 `can_start`，
排期排在 `start` 之前会被 `qyn_review` 拦（`before_start`）—— 别绕过它。

★★ **用户没说的，一个字都不登记；看不懂的简写先问。**（2026-10-22 实测）

那一轮用户只写了「示例课程G写。」，我却推出"示例课程G作业"并写进回复 —— 用户当场反问
「什么叫示例课程G作业？我没说过！」。前因是库里早先有三条把**课程名当任务**的条目
（`示例课程G…概论`，每周四一条），我凭它们反推"有个示例课程G作业"。

- **简写到看不懂就问**："示例课程G写"= 写进课表？还是登记作业？一句反问胜过猜错。
- **课表里的课程不是任务**：绝不凭课表/库里的课程条目反推"有个作业/有个截止"。
- **只做这一轮明确要求的事**：用户明确说过「你不要着急更新下周的教室因为每周教室不一样」
  —— 教室以**当前周原图**为准，不提前改下周；"按照课表来"就是清单照抄，不自作聪明。
- **同名条目不止一条时**，先 `context` / `show` 回读确认它到底是什么，再决定动不动。
- 用户连续纠正（"不不不"、"我没说过"）时，**先停下重述我的理解**，别继续动手。

★★ **锚只能锚到同一门课。锚不上就停下来问，绝不拿别的课凑。**（2026-10-21 血的教训）

- 用户的图/话明确是**示例课程A**的作业 ⇒ 它就只能挂到 `示例课程A` 的课次上。
  **不许**因为"示例课程A下一节课不在课表里"就改成挂**示例课程**的课 —— 那会把 A 课的作业
  登记成 B 课的，日期、地点、截止那句 due_time 全跟着错。
- 锚不上的**真实原因**通常是：**课表只录到这周**，下周那门课的课次还没进来。
  内核会在 `qyn_anomalies` 里报 `periodic_unanchored`，文案已经分清两种：
  · 「课表里没有…的**未来**课次了（课表覆盖到 X）」⇒ **该让用户补下周课表**
  · 「未来课次都已物化过」⇒ 这次不必再物化，不是数据问题
- 锚不上时的**正确动作**（按顺序）：
  1. 直接用 `date` 写**截止日**（用户说"下周一交"就写 10/26），`follow_course` 那个周期任务先不管
  2. **回询用户**要下周课表（一句话："下周课表还没录，补一下我才能自动排"）
  3. 绝不"猜一个最近的课"当锚

如果你**已经手工登记过这一次**，又注册了周期任务，内核**不会**替你认定它们是同一件事 ——
它只说"这一天已有同名条目，**没有**再物化一条"（`already_present`）。然后由你决定：

- 它**就是**这个周期任务的这一次 → `qyn_apply` 里给它补 `occurrence_of` + `anchored_to`
  （**认领**，之后 sync 不再报）
- 它其实是**另一件事** → 改名，或另立一个周期任务

内核只在**机制**上兜底：同一次发生**不会**被物化两条（否则按名字的 `qyn_mark` /
`list.upsert` 只命中第一条）。它**不查**"是不是重复"——那是你的判断。

两种写法，**挑你不容易出错的那种**：

| 场景 | 写法 |
|---|---|
| 录一整周课表 / 换整份规则 | 数组 = **整段替换** `{"dated_sessions": [...]}` |
| 改一两处（换教室、调休、改期） | `{"upsert": [ ... ], "remove": [ ... ]}` = **增量，只写要改的那几条** |

```jsonc
{"schedule": {"sessions": {"upsert": [{"date":"2026-10-14","periods":"5-8",
                                        "course":"示例课程F","location":"示例教室X1"}]}}}
{"schedule": {"sessions": {"remove": ["2026-10-14|5-8"]}}}          // 停课/删掉一节
{"schedule": {"periodic_tasks": {"upsert": [{"task":"示例课程A作业",
    "follow_course":"示例课程A","due_time":"23:59"}]}}}      // 周期作业
{"rules": {"planning_rules": {"upsert": [{"id":"rule-002","kind":"preference",
    "condition":"中午没课","body":"优先安排示例课程作业"}]}}}
{"list": {"upsert": [{"task":"…","date":"2026-10-15","detail":{…}}]}} // 登记/改期
```

`periodic_tasks.remove` / `planning_rules.remove` / `list.remove` 同理（给名字或 id）。
**完整示例见 `qyn_apply` 的工具描述** —— 那里才是每轮都在的资料。
先全量校验再落盘，任一处不合规则**一个字节都不写**；写错键名会明确报"不认识的键"。

## 注册表 · `gist` 与 `detail`

条目 = 内核字段（`task` / `date` / `due_time`，可选 `priority` / `lead_days`）+ 两个载荷：

| 字段 | 装什么 | 进不进默认视图 |
|---|---|---|
| **`gist`** | **一行可执行要点**（≤60 字）：题号 / 页码 / 交法 / 在哪交 | ★ **进** —— `active` 里自带 |
| `detail` | 全部原始信息：题号、页码、提交要求、来源、判分规则… | 不进（太大）—— 要它用 `qyn_show` |

★ **`detail` 按需取**：列表里的 `gist` 够答绝大多数问题。**用户问到哪一件才 `qyn_show` 那一件**，
不要为了"看得更全"把清单每条都拉一遍。

### 两层结构：DDL 在注册表，建议时段在计划里

| 层 | 装什么 | 谁写 |
|---|---|---|
| **注册表** `date` / `due_time` | **DDL（硬截止）** —— 用户说的 / 截图给的 / 课次推的 | 有就写，**没有就不写** |
| **计划** `slots` | **我建议的时段**（什么时候做）—— 随时重算、可整个丢掉 | 每次重排都重写 |

★ **绝不把建议时段写回 `date`/`due_time`** —— 那是给自己造 DDL：
内核会拿它算紧迫度，于是"其实不紧急的复习"越接近越急、自己浮到清单最前面
。
没有 DDL 的条目**不参与紧迫度排序**（内核给 `later`、理由"没有硬截止"），
但它**照样能排进 `slots`** ✓ —— 这才是"建议时间"该待的地方。

```jsonc
{ "task": "示例课程C 作业3", "date": "2026-10-15", "due_time": "上课前",
  "lead_days": 2,
  "gist": "Pxx 第 1/2/3 题，一页 A4，写学号姓名",
  "detail": { "pages": "Pxx", "problems": ["5","6","7","10","12","15"],
              "submission": { "paper": "一页A4", "must_write": ["学号","姓名"] },
              "source": "PPT 截图（作业 3/7）" } }
```

- **`gist` 一定要写**（尤其作业/考试）：用户问"现在做什么"时，答的是能**照着做**的信息。
  只说"示例课程A作业"他动不了手，还得再问一次题号。
  写在**登记那一刻**，一次成本；之后每次读都自带，不必为每条再 `qyn_show`。
  背景与出处**不要**塞进 `gist`（那是 `detail` 的活）。
- 周期任务上也可以写 `gist` —— 物化这一次发生时**自动复制**过去。
- **`detail` 仍然要写全**：图上、话里的信息**全部**进去，**不要压成一句话**。
  它是"以后再问起来还能答"的唯一依据。
- **`priority` 别默认填**。只有用户**明确**说过"这事重要"才给 —— 随手填 `medium` 是编信号。
- **`lead_days`**：这件事需要提前几天准备（报告 / 论文 / 复习）。**你判断语义，内核做算术** ——
  它据此把紧迫度抬高并写进理由。

`qyn_state` 给的是列表视图（`gist` 在里面、`detail` 只给 `has_detail` 标记）；
完整结构体用 `qyn_show({task})` 取。

## 现在几点 · 紧迫度（内核算，不用你填）

**每次读取都带 `now`**（日期、时刻、周几、时段）。规划是**时间相关**的，别自己估时间：
`why` 里的剩余时间是**相对 `now`** 算的 —— 同一个任务，早上问和深夜问，余量和档位都不同。

清单上的条目**必然**未完成，所以视图里**没有 `status`**；轻重也不是你填的 `priority`，
而是内核算出来的 **`urgency` + `why`**，并且**已按它排好序**：

```
now = 2026-10-10 23:13 周六 深夜
[soon  ] 10-12  示例课程A作业   还剩 34 小时、你标为高优先级
[soon  ] 10-12  示例课程B 第二次作业 还剩 2 天、你标为高优先级
[normal] 10-15  示例课程C 作业3    还剩 4 天
```

四档：`urgent` / `soon` / `normal` / `later`。决定档位的（全在 `why` 里说清）：
**剩余小时数**、`lead_days`、以及用户明确标过的重要性。
不到 2 天说**小时**，更远才说天 —— **只有"还剩…"，没有"已过…"**：
过点的条目已经翻篇（见「先读这几条」第 4 条），**根本不会出现在任何视图里**。

**课次也按时刻**：`qyn_sessions` 只给**还没下课**的（今天早上那节到晚上就不列了），
每节带 `starts_in`。`now` 是唯一参照 —— 不要用"今天/明天"这种模糊说法替它判断。

**你要做的**：排序已经给你了 —— 直接按它出规划；有异议时先看 `why` 里是哪一项不对
（多半是 `lead_days` 没给，或日期不对），**改数据而不是改顺序**。

## 哪些进上下文、哪些不进

| 东西 | 进不进 | 怎么取回 |
|---|---|---|
| 日期已过的注册 | **不进** `active`（等效隐藏，不报逾期） | `qyn_history --days N` |
| 归档（更老的） | **不进**任何视图 | `qyn_history`（按月分文件） |
| 某条的完整 `detail` | 不进列表 | `qyn_show --task <名>` |
| 课次 | 不进 `qyn_state`（只给最近一节 + 总量） | `qyn_sessions --days N` |

★ 单次上限：`history` 50 条、`sessions` 60 节 —— 超了返回 `more` / `capped_at`，按需放宽。

## 规则怎么写

`planning_rules` 每条四个键：`id` / `kind`（`preference` 软偏好 或 `constraint` 硬约束）/
`condition` / `body`（自然语言，内核不解释，你按它排）。

- ★ **「某时段不排」这类规则必须填 `no_slots`**（如 `["19:00-23:59", "00:00-06:00"]`）——
  自然语言的 body 内核不解释，**只有 `no_slots` 能被 `qyn_review_plan` 机械校验**；
  不填就等于没有这道闸。`kind: constraint` 违反 ⇒ 报冲突，`preference` 违反 ⇒ 报警告
- 长期规则 ⇒ 写进 `rules.json`；一次性的例外 / 跨多轮的临时约束 ⇒ **只进计划的 `focus`**
- `scope.task` / `scope.course` 必须是系统里已存在的名字，否则规则永不生效；拿不准就留空 `scope`
- 用户指着某条说"这条删掉" ⇒ `planning_rules.remove` 删那条，删完**重排**

## 看图（主动性）

用户给图往往只说"记一下"。**自己判断这是什么**（作业通知 / 考试 / 临时提醒 / 课表），
把有用信息提炼进结构体，决定进 `schedule` 还是 `list`，然后走 `qyn_apply`。

作业 / 考试 / 临时提醒：直接按下面「作业 / 考试定日期」的规矩登记。

**课表图**：整条读图→录入流程（切片放大、分批写、标水课、回读核对）在技能
**`qyn-timetable`** 里 —— 加载它再动手，别照记忆猜形状。

## 口语里的"周"

周次不许、周几可以（`weekday`）、"这周/下周"由我落成具体日期（见「先读这几条」第 2 条）。
落日期时用 `qyn_state.now` 里的**今天日期 + 周几**推算，**不心算**；日期只来自：
截图 / 用户口述 / 已给日期加减。

## 作业 / 考试定日期

不推周，锚课次：

```jsonc
{"schedule": {"periodic_tasks": {"upsert": [
  {"task":"示例课程A作业", "follow_course":"示例课程A", "due_time":"23:59"}]}}}
```

锚不到（没给 `follow_course` 或课表无此课）→ 内核报 `periodic_unanchored` → 问用户。
一个周期任务同时只留**一件**待办。

调休 / 放假 / 调课 = **只改那一条**：改期用 `list.upsert` 换日期；跳过用 `qyn_mark` 标 `cancelled`。

## 规则

`kind`：`preference` 软偏好 / `constraint` 硬约束。
`scope.task` / `scope.course` 必须是**系统里已存在的名字**，否则规则永远不生效；拿不准就留空 scope。

## 到点唤醒（自动规划）

唤醒时刻**跟着规划走，不是固定定时器**（用户 2026-10-15）：内核 `next-tick` 读最新快照，
算出「第一块**结束时刻**晚于现在」的那一刻；控制层到点把这一轮叫起来，跑完再排下一次。
每日 07:00 是锚点；每 30 分钟的守卫只补链条（边界没到就什么都不做，不花 token）。

被这样叫起来时（提示词会说明是哪种）：

- **默认用户没做完**：**不要**把那一块标记完成 —— 把它往后挪到合适的空档，
  重排剩余时间，存新快照（顺序仍是「重排 → 存快照 → brief」）。
- **默认不发消息**；只有「排不下 / 今天到期的活没排上 / 需要用户决定」时才发一句。
- 不要去问「上一块做完了吗」——除非你要据此改别的决定。

## 重排：怎么写、什么时候写

注册表一变（登记 / 完成 / 取消 / 改期）就**重排**，别在旧计划上打补丁。步骤：

1. 重新读 `qyn_state`（+ 需要时 `qyn_sessions`）
2. 从头算一遍（不要拿旧计划的时段接着用）
3. `qyn_plan_snapshot` 存新快照 —— **规划真的变了才存**
4. 再回答用户

写操作的返回值带 `plan_invalidated: true`（**事实**：注册表变了）—— 看到它就重算
（`qyn_apply` / `qyn_mark` / `qyn_sync` 都有；no-op 的写不带）。

★ **排期不要写回 `date` / `due_time`**（见上「两层结构」）。


## 怎么排：先过规则 → 看空档 → 估时长 → **往多排**

**第 0 步（不要跳过）**：把 `planning_rules` 过一遍 —— 它们是**约束**，不是背景资料。
排出来的每一块都要先满足它们（"晚上不排活"⇒ 晚上一块都不排）。

1. **看空余时段**：课表（`qyn_sessions`）+ 今天还剩多少时间 + 已经排出去的那些。
   先分清空档是**碎片**（两节课之间、饭后、睡前）还是**整块**（一个下午）。
2. **估这件事要多久**：轻活按**分钟**算（线上提交 / 注册 / 填表 / 交作业 —— 十几分钟就够），
   学业活按**小时**算（作业、报告、复习）。
   **估出来的分钟数写进 `estimate_minutes`**（条目的顶层字段；周期任务写在
   `periodic_tasks` 条目上，物化时自动带下来）—— 不要再塞 `detail`，也别只留在脑子里：
   写进去之后 `qyn_review` 会把「块比预留时长短」报成警告，`qyn_context` 也会透出来。
   用户直接给过数字时（「示例课程F以后预留一小时」「预习报告预留半小时」）
   ⇒ **照他说的写**（60 / 30），不要自己改。
   ★ 别把它写成时段：`estimate_minutes` 是"要多久"，"几点做"只进规划的 `slots`。

★ **往多排**：宁可多留，不要排得刚好。**做不完不影响任何东西** —— 注册表不变、
任务不会消失、紧迫度自己往上浮，过段时间重排就行。
排太紧的代价才是真的：一有意外就全线延误，看着永远做不完。

★ **先找整块，实在排不下才拆**（优先级：整块 > 拆分 > 报告）。拆分是**最后手段**，
  不是第一反应 —— 一份能一口气做完的作业，不要拆成三块塞进三个空隙。
★ **课间禁排（硬约束，不是建议）**：同一天两节课之间的空隙、去上课的路上**一律不排**
  —— 课间要改教室、要转场，没时间写东西。判据：整块落在同一天两节课之间且空隙 <60 分钟
  ⇒ `qyn_review_plan` 报 `in_class_gap` **冲突**（`brief` 也会拒绝出正文）。
  长空隙（如午休 2.5 小时）不算课间，正常可用。
★ **水课 = 可用但不建议**（和「13:00-14:00 尽量避免」同类）：`water: true` 的课（如示例课程G）
  不算撞课，但审查会给 `water_class` 警告 ⇒ **只排不费脑的活**（写作业可以，做实验报告不行）；
  能不用就不用，实在排不下才用它（并在回复里说明）。
★ **短活可以单列**：十几分钟的事（取包裹、线上提交）就单独占一小块，
  **不要**硬塞进大块里 —— 短不是问题，只有**课间**不能排。
★ **轻活不占整块**：十几分钟的事塞进**碎片空档**，不要给它单独留一小时。

★ **整块的活不要塞碎片**：复习、写报告要 2 小时起 —— 塞进半小时的空隙等于没排。
一件大事做不完就拆成两次，每次一块，做完一次再排下一次。

★ **水课可以拿来做事**：课表里标了 `water: true` 的课（示例课程G这种一上三小时的），
课上能做**作业性**任务 —— 把它当**可用时段**，能写掉一份作业。
需要专注的活（复习、写报告）**不要**排在水课里。

★ **排不下时的放宽顺序**（一级一级放宽，能排下就停）：

```
① 动用中午（11:50-13:00）—— 平时不排，排不下时才用
② 拆分：1 小时 + 半小时，放到**两天的中午**
③ 还排不下 ⇒ 报告（说清哪件事、卡在哪个 DDL、可选方案），不要硬塞
```

★ **同一件事最多重排 2 次**（**工具会强制**：最近 30 分钟存了 ≥3 份快照 ⇒ `brief` 直接
  返回 `kind=loop` 把你拦下，那时只能去报告）。两次还排不下 ⇒ **报告**（卡在哪 + 2–3 个可选方案），
  不要反复试（实测一轮试了 17 次）。
★ 排完先 `qyn_review_plan` 审一遍（conflicts 与 warnings 都要消掉）再交出去（`qyn_review_plan`：撞课 / 时段重叠 / 漏排）——
有冲突就**重排**（regen），别把冲突写给用户看。**用户看到的规划必须是干净的。**

## 规划快照的**契约**（形状不许自己发明）

`qyn_plan_snapshot` 存下来的规划，**内核要读回来**（`qyn_state.last_plan`）——
所以正文形状不是自由的，认这几个键：

```jsonc
{ "focus": "一句话主旨",
  "horizon": "2026-10-11 至 2026-10-16",
  "order": ["最紧的", "其次", "…"],                     // 任务名，按优先级
  "slots": [ { "date": "2026-10-12", "time": "14:00-16:00",
               "task": "示例课程B 复习（2小时）", "why": "当天 14-16:30 空档" } ] }
```

- **`slots` 必须有**：内核靠它把"什么时候做什么"还给下一轮的你。
  没有它，你下一轮**看不见自己排过什么** —— 只能靠对话记忆复述，
  用户提前做完事时就会"抱着旧安排不放"。
- `task` 用**注册里的名字**（别写"示例课程F（线上提交）"这种加后缀的变体）——
  内核按名字集合比对，写法不同会被当成"计划里有、活跃里没有"。
- 其余键（`note` / `rules_applied` / `conflicts`…）随你加，内核不读也不管。
- **只在规划真的变了时才存快照** —— 只是读一遍数据不必存。

## 每日检查

0. 先过一遍 `planning_rules` —— 它们是**硬约束**，不是背景资料。
   排任何时段之前先满足它们（例："晚上不排活" ⇒ 晚上一个时段都不许排）。
   规则就在 `qyn_state` 的返回值里，别跳过。
1. `qyn_sync`
2. `qyn_anomalies`（为空就如实说"无异常"）
3. `qyn_state` —— `last_plan` 是**上次那份派生物**：
   · `slots` = 上次排的时段（每项带 `passed`：那个时段过了没有）；`order` = 上次的优先级
   · ★★ **它只用来对账，不是这次排期的底稿** —— 拿它的时段接着用，就是"在史山上继续修建"
   · ★ **差异要你自己比**：`slots`/`order` 里的任务 vs `active` 里的任务 ——
     谁做完了（那些时段空出来，把后面的事**提前**）、谁排过却没做（**往后延**）、
     谁没进计划。内核不替你比（那是判断）
4. `qyn_sessions`（不要只看本周）
5. **从头重排** → `qyn_plan_snapshot`；按「输出格式」的三种形状展示（规划 / 日程 / 待办）
6. `qyn_history` 里**滚出时仍未处理**的、以及「久未维护」—— 不要自行清理或改状态，列出来问用户

★ **"现在做什么"要重新算一遍，不是复述上一份规划**。用户每完成一件事、每取消一次，
  可用时段就变了 —— 该做的是**把后面的事往前提**，然后重存快照。
  复述旧安排看起来"没变"，但那是**没在安排**。

**你负责语义**：课程时间部分重叠、同义任务名、调休导致的课表与截止日不符、模糊的调整要求。
日期比较、状态迁移、名称集合运算 —— 交给内核。

## 水课标在**课程**上（不是课次）

用户 2026-10-16：「这种明显要跟着课程不是课次」。

- 写入：`{"schedule": {"courses": {"upsert": [{"course": "课程全名", "water": true}]}}}`
  —— 标一次，该课**所有**课次（含以后课表里新加的）都算水课。
- 课次上单独写 `water: true` 仍然认（历史数据与个别例外）。
- 内核里判据只有一份（`_is_water`）：课间判定、课次视图、`review` 的 `water_class` 警告、
  `brief` 的「（课·水）」标记四处同口径。
- 语义不变：水课**可用但不建议** —— 只排不费脑的活；`water_class` 是警告、不是撞课。

## 导入新一周课表：用 `sessions.upsert`（不是 `dated_sessions`）

用户 2026-10-16 报的严重问题：「传入新一周课表后旧课表直接报废了，今天明明有课，
但传入新课表后被认为没课，新课从 19 日开始」。

- `dated_sessions` = **整段替换**（整张课表换掉）⇒ 拿它导入新课表会把**本周课次整批删掉**。
- 导入新一周 ⇒ `{"schedule": {"sessions": {"upsert": [...]}}}`（只加不删）。
- 内核现在会**拦住**"整段替换会删掉今天及以后的课次"这一情形，并指路 `sessions.upsert`；
  确实要整段替换，就把 `"replace_future": true` 一起写上（只删**已过去**的课次不拦）。
